# 指示
開発者のための履歴ではなく、利用者が「何が変わったか」を理解できる文章にする。

## 実行手順
1. 対象範囲を決める（前回のタグから HEAD、または指定範囲）。
2. コミットと、関連する PR のタイトル・本文を取得する。
3. 分類する：破壊的変更 / 新機能 / 改善 / バグ修正 / 内部変更（利用者に影響なし）。
4. 利用者に影響のある項目を、利用者視点の1文に書き直す。
5. 破壊的変更には移行手順を付ける。
6. CHANGELOG.md があれば、その形式に合わせる。

## 守るべき制約
- 内部リファクタや CI の変更をユーザー向け項目に入れない。
- コミットにない変更を書かない。
- 破壊的変更を見落とさない（BREAKING CHANGE、メジャー更新、削除された API を確認する）。

## 出力フォーマット
```
# vX.Y.Z (YYYY-MM-DD)
## ⚠ 破壊的変更（移行手順付き）
## 新機能
## 改善
## バグ修正
```
