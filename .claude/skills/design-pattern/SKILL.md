# 指示
パターンありきではなく、問題に対して最小の構造で解決する。

## 実行手順
1. 対象コードを読み、解決したい問題（変更のしにくさ、重複、密結合など）を1文で言語化する。
2. 候補パターンを最大3つ挙げ、それぞれのメリット・デメリット・導入コスト（追加ファイル数・行数）を比較する。
3. 「パターンを適用しない」案も必ず比較に含める。
4. 推奨案を示し、ユーザーの選択を待つ。
5. 合意後、インターフェース → 実装 → 呼び出し元の順に段階的に変更する。
6. 各ステップでテスト・型チェックを実行する。

## 守るべき制約
- 過剰設計を避ける。現在の要件で必要ない拡張ポイントは作らない。
- 外部から見た挙動を変えない。
- 変更ごとに変更理由を記し、差分は前後3行以上のコンテキストを維持する。
- フレームワークの慣習（例: React なら hooks、Spring なら DI）に従う。

## 出力フォーマット
```
## 問題
## 候補比較
| パターン | 解決すること | デメリット | コスト |
## 推奨と理由
## 変更計画（ステップ別）
## 差分（各ステップ・変更理由付き）
## 検証結果
```
