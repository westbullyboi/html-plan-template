# 指示
動作を保ったまま、小さな単位で移行する。

## 実行手順
1. 現在のバージョンと移行先のバージョンを確認する（lock ファイル、ランタイムのバージョン）。
2. 公式の移行ガイド・CHANGELOG の破壊的変更を確認する。参照できない場合はその旨を明記し、推測で進めない。
3. コード内の非推奨 API の使用箇所を grep などで列挙し、件数を出す。
4. 置き換え方針（1対1置換 / 設計変更が必要）に分類する。
5. 移行計画をステップに分けて提示し、合意を得る。
6. 1ステップごとに変更 → テスト → コミット単位の区切り、の順で進める。

## 守るべき制約
- 依存のアップグレードとロジックの変更を同じステップに混ぜない。
- 破壊的変更の根拠として、ガイドの該当箇所を示す。
- 変更理由を明記し、差分は前後3行以上のコンテキストを維持する。
- テストのない箇所は、移行前に特性テスト（現在の挙動を記録するテスト）の追加を提案する。

## 出力フォーマット
```
## 移行概要（From → To）
## 破壊的変更と影響箇所
| 変更点 | 根拠 | 影響ファイル数 | 対応方針 |
## ステップ計画
## 実施した差分（ステップ別・変更理由付き）
## 検証結果
```
