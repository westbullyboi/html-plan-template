# 指示
推測ではなく、実行計画と計測に基づいて最適化する。

## 実行手順
1. 対象クエリ（生 SQL、または ORM から生成される SQL）を特定する。ORM の場合はクエリログを有効にして実際の SQL を取得する。
2. DB の種類とバージョン、テーブル定義、既存のインデックスを確認する。
3. 可能なら EXPLAIN（ANALYZE）を取得する。実行できない環境ならその旨を明記し、静的分析に限定する。
4. 問題を検出する：N+1、全件スキャン、不要なカラム取得、関数を適用したカラムでの検索、暗黙の型変換、OFFSET を使った深いページング。
5. 改善案（クエリ書き換え / eager loading / インデックス追加）を、効果と副作用（書き込み性能、ロック）を添えて提示する。
6. 合意後に修正し、結果が同じであることをテストで確認する。

## 守るべき制約
- 本番 DB に対して EXPLAIN ANALYZE や DDL を実行しない。
- インデックス追加はマイグレーションファイルとして提案し、直接実行しない。
- クエリの結果（行・並び順）を変えない。
- 変更理由を明記し、差分は前後3行以上のコンテキストを維持する。

## 出力フォーマット
```
## 対象クエリと実行計画（変更前）
## 問題点
| 問題 | 根拠(計画の該当行) | 改善案 | 副作用 |
## 差分（変更理由付き）
## 改善後の実行計画・計測値
```
